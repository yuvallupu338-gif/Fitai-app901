# יופי — רשת חברתית והזמנות לבעלי מקצוע בתחום היופי והטיפוח

אפליקציית ווב מלאה (Production‑Ready) המשלבת **רשת חברתית** לבעלי מקצוע בתחום היופי
והטיפוח יחד עם **מנוע חיפוש, הזמנת תורים, טיפולים בבית הלקוח ומפגשים קבועים**.

האפליקציה כתובה **כולה בעברית ובכיוון RTL**, בנויה Mobile‑First, ניתנת להתקנה בטלפון (PWA),
ועובדת מול מסד נתונים אמיתי — **אין באפליקציה נתונים קשיחים בקוד**. כל בעל מקצוע, שירות,
פוסט, הזמנה, הודעה או ביקורת מגיעים ממסד הנתונים ונוצרים דרך הממשק.

## מה נבנה

### רשת חברתית
- **פיד** עם שלוש לשוניות: *בשבילך* (רלוונטיות לפי עיר ותחומי עניין), *עוקב* (רק מי שאני עוקב אחריו) ו*פופולרי*.
- **כרטיס פוסט עשיר**: גלריית מדיה, שם ותמונת בעל המקצוע, עיר, סוג הטיפול, מחיר משוער,
  לייק, תגובות, שמירה, שיתוף — וכפתור **"הזמן טיפול דומה"** שמעביר ישירות לזרימת ההזמנה עם השירות המתאים.
- יצירת פוסט עם העלאת תמונות, קישור לשירות, האשטגים, טיוטה ותזמון פרסום.
- **פוסטים מוצמדים** (עד 3), סידור מחדש של תיק העבודות, ומדדי צפיות/לייקים/שמירות/הזמנות לכל פוסט.
- מעקב, ביטול מעקב, שמירת פוסטים, שמירת בעלי מקצוע, חסימת משתמשים ודיווחים.

### פרופילים
- **פרופיל משתמש רגיל**: שם, שם משתמש, עיר, ביו, אווטאר, עוקבים/נעקבים, פוסטים שמורים, ביקורות שכתב.
- **פרופיל בעל מקצוע**: תמונת נושא, תיאור, מקצועות, שנות ניסיון, שירותים ומחירים, אזורי שירות,
  שעות פעילות, תיק עבודות, דירוג ממוצע ופילוח דירוגים, זמן תגובה ממוצע, תגי אימות,
  וכפתורי **הזמנת תור / הודעה / מעקב / שיתוף / דיווח**.
- **חשבון אחד לשני המצבים** — משתמש רגיל ובעל עסק. **ההרשמה מבקשת רק שם, שם משתמש
  וסיסמה**; העיר ושאר הפרטים מושלמים בהגדרות, ומשם גם נפתח הפרופיל העסקי — בכל שלב
  שהמשתמש יבחר. אפשר להחליף מצב מהתפריט ולהשהות את הפרופיל העסקי בלי למחוק את החשבון.

### חיפוש
- חיפוש חופשי עם **השלמה אוטומטית** (בעלי מקצוע, מקצועות, ערים, שירותים).
- מסננים: מקצוע, עיר, מרחק, טווח מחירים, דירוג מינימלי, זמינות (היום / השבוע / תאריך ספציפי),
  סוג מיקום (בקליניקה / בבית הלקוח / שניהם), אימות, ותת־שירות.
- מיון לפי רלוונטיות, דירוג, מרחק, מחיר, פופולריות או חדשים.
- **חיפושים אחרונים**, **חיפושים פופולריים** (נצברים אמיתית במסד) ו**חיפושים שמורים עם התראות**.

### הזמנות
- **הזמנה חד־פעמית**: בחירת שירות → מיקום (קליניקה / בית הלקוח) → כתובת → בורר מועדים שמציג
  **רק שעות פנויות אמיתיות** מהיומן → הערות → מסך סיכום עם מחיר כולל, זמן נסיעה ומדיניות ביטול.
- **הכתובת המלאה נחשפת רק אחרי אישור ההזמנה** — לפני כן מוצג רק אזור כללי.
- **מכונת מצבים מלאה**: `pending → confirmed → on_the_way → arrived → in_progress → completed`,
  לצד `declined`, `cancelled_by_client`, `cancelled_by_pro`, `no_show` — עם **היסטוריית סטטוסים** מלאה.
- **מפגשים קבועים**: שבועי / דו־שבועי / כל שלושה שבועות / חודשי / מותאם אישית,
  תצוגה מקדימה של כל התאריכים, **דילוג או הזזה של מפגש בודד**, אפשרות "החל על כל המפגשים הבאים",
  אישור דו־צדדי לפני הפעלה, והשהיה/ביטול של הסדרה.
- **לוח זמנים לבעל המקצוע** שמונע הזמנה כפולה, הזמנה בזמן חסום, מחוץ לשעות הפעילות
  או ללא זמן נסיעה מספיק — האכיפה נעשית ברמת מסד הנתונים (`EXCLUDE ... USING gist`).
- **לקוחות קבועים** עם הערות פרטיות של בעל המקצוע.

### תקשורת
- **צ׳אט בזמן אמת** בין לקוח לבעל מקצוע, כולל **הודעות מערכת** אוטומטיות
  ("ההזמנה אושרה", "בעל המקצוע בדרך", "המפגש הועבר").
- **התראות** על מעקב, לייק, תגובה, הודעה, הזמנה חדשה, שינוי סטטוס, תזכורות וביקורות.

### ביקורות
- ניתן לכתוב ביקורת **רק אחרי טיפול שהושלם** (נאכף בטריגר במסד).
- דירוג כולל + פילוח (מקצועיות, יחס, ניקיון, דיוק בזמנים), תמונות, **תגובה אחת** של בעל המקצוע,
  ועדכון אוטומטי של הדירוג הממוצע ומספר הביקורות.

### ניהול
- **לוח בקרה למשתמש**: התורים הקרובים, היסטוריה, סדרות קבועות, שמורים, כתובות.
- **לוח בקרה לבעל מקצוע**: בקשות חדשות, יומן, לקוחות קבועים, שירותים, ביקורות,
  ונתונים מקצועיים (צפיות בפרופיל, הזמנות, שיעור אישור, הכנסה משוערת, טיפולים שהושלמו).
- **פאנל ניהול מוגן**: סטטיסטיקות, משתמשים, בעלי מקצוע, **אישור מקצועות חדשים**, אימותים ודיווחים.

```

  (main)/            כל האפליקציה המחוברת
  api/auth/token     הנפקת אסימון Supabase ללקוח (Realtime)

  actions/           Server Actions — כל פעולת כתיבה עוברת דרך כאן
  data/              שאילתות קריאה לשרת (Server Components)
  auth/              סיסמאות, JWT, סשנים, הרשאות
  supabase/          יצירת לקוחות (דפדפן / שרת / service‑role)
  validations.ts     כל סכמות ה־Zod
hooks/               use-realtime, use-refresh-on-focus, use-infinite-scroll, ...
supabase/
  migrations/        13 קובצי מיגרציה
```

### עקרונות

- **כתיבה רק דרך Server Actions.** הדפדפן אף פעם לא כותב ישירות למסד.
  כל פעולה מחזירה `ActionResult` אחיד (`ok` / `error` / `message`) עם הודעות בעברית.
- **קריאה דרך Server Components** עם `lib/data/*`, כך שהדף מגיע ללקוח מוכן ומהיר.
- **Realtime בנוסף, לא במקום.** כל מסך מתרענן גם באירוע Realtime, גם בחזרה למסך (focus/visibility),
  גם אחרי פעולה וגם במשיכה מטה (pull‑to‑refresh) — כך שהאפליקציה מתעדכנת גם כשה־socket נופל.

## מסד הנתונים

**48 טבלאות** בסכמת `public`, כולן עם `id uuid primary key default gen_random_uuid()`,
מפתחות זרים, אינדקסים, `created_at` / `updated_at` (מתוחזק בטריגר), ו־`deleted_at` למחיקה רכה
בטבלאות התוכן.

### קבוצות הטבלאות

**זהות והרשאות**
`profiles` · `usernames` · `cities` · `recovery_codes` · `auth_sessions` · `login_attempts` ·
`security_events` · `rate_limits`

**בעלי מקצוע**
`professions` · `profession_requests` · `professional_profiles` · `professional_contact_details` ·
`professional_professions` · `professional_services` · `service_areas` ·
`professional_availability` · `unavailable_dates` · `professional_verifications` ·
`phone_verification_codes`

**חברתי**
`follows` · `blocked_users` · `professional_posts` · `post_media` · `post_likes` · `post_comments` ·
`saved_posts` · `saved_professionals` · `profile_views` · `post_views` · `saved_searches` ·
`search_history` · `popular_searches`

**הודעות**
`conversations` · `conversation_members` · `direct_conversation_keys` · `messages`

**הזמנות**
`service_addresses` · `bookings` · `booking_status_history` · `recurring_booking_series` ·
`recurring_booking_occurrences` · `customer_notes`

**ביקורות, התראות ובטיחות**
`reviews` · `review_replies` · `notifications` · `reports` · `push_subscriptions` · `activity_log`

### לוגיקה במסד (ולא רק בקוד)

- **מניעת חפיפה בהזמנות** — אילוץ `EXCLUDE USING gist` על `(professional_id, tstzrange(scheduled_start, blocked_until))`
  לסטטוסים הפעילים. `blocked_until` הוא עמודה שמתוחזקת בטריגר (`scheduled_end + זמן נסיעה`),
  כי `timestamptz + interval` אינו `IMMUTABLE` ולכן אינו יכול להופיע ישירות באילוץ.
- **מוני עוקבים / לייקים / תגובות / שמירות** מתוחזקים בטריגרים, לא בשאילתות `count(*)`.
- **דירוג ממוצע ומספר ביקורות** מתעדכנים אוטומטית בכל שינוי בביקורת.
- **`professional_readiness()`** מחשב אחוז השלמה ורשימת חוסרים; **`guard_professional_publish()`**
  לא מאפשר לפרסם פרופיל שאינו עומד בתנאים (תמונה, מקצוע, שירות עם מחיר, עיר ואזורי שירות, 3 תמונות עבודה).
- **`guard_booking_update()`** אוכף מי רשאי לשנות מה: לקוח אינו יכול לאשר הזמנה או לשנות מחיר,
  בעל מקצוע אינו יכול לשנות את פרטי הלקוח, והכתובת המלאה נחשפת אוטומטית ברגע האישור.
- **פונקציות שירות (RPC)**: `search_professionals`, `search_suggestions`, `feed_posts`,
  `similar_professionals`, `rating_breakdown`, `check_booking_slot`, `available_slots`,
  `preview_series_dates`, `generate_series_occurrences`, `materialize_series_bookings`,
  `admin_stats`, `consume_rate_limit`, `record_profile_view`, `record_post_view`, `log_search`.

## אבטחה ופרטיות

| נושא | היישום |
|---|---|
| סיסמאות | **scrypt** (`node:crypto`) עם מלח אקראי ופרמטרים המוטמעים במחרוזת ה־Hash. השוואה ב־`timingSafeEqual`. **סיסמה לעולם אינה נשמרת כטקסט.** |
| קוד שחזור | נוצר אקראית, **מוצג פעם אחת בלבד**, ובמסד נשמר **רק ה־Hash** שלו. ניתן להחליף אותו מההגדרות. |
| סשנים | אסימון אקראי (32 בתים) בעוגייה `httpOnly` + `SameSite=Lax` + `Secure` בייצור. במסד נשמר רק ה־SHA‑256 שלו, עם אפשרות לנתק מכשירים והיסטוריית התחברויות. |
| הגבלת קצב | `consume_rate_limit()` במסד — על התחברות, הרשמה, שחזור, שליחת הודעות והזמנות. |
| נעילה זמנית | אחרי מספר כשלונות רצופים החשבון ננעל לזמן קצוב, עם הודעה ברורה בעברית. |
| מפתחות סודיים | `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET` ו־`AUTH_SECRET` **נקראים בשרת בלבד**. לדפדפן מגיעים רק `NEXT_PUBLIC_SUPABASE_URL` ו־`NEXT_PUBLIC_SUPABASE_ANON_KEY`. |
| RLS | מופעל על **כל** הטבלאות, עם מדיניות לפי בעלות והשתתפות, ופונקציות עזר `SECURITY DEFINER` (`current_profile_id`, `owns_professional`, `is_conversation_member`, `is_booking_party`, `can_view_post`, `can_view_address`, `is_admin`). |
| הרשאות ברמת עמודה | `revoke select on profiles` ואז `grant select (...)` רק על העמודות הציבוריות — כך ש־`password_hash` ושאר השדות הרגישים **אינם ניתנים לקריאה כלל** דרך ה־API, גם אם תישכח מדיניות. |
| פרטים אישיים | טלפון וכתובת הקליניקה יושבים בטבלה נפרדת (`professional_contact_details`) עם RLS משלה. כתובת מלאה של הלקוח נחשפת רק אחרי אישור ההזמנה. |
| בדיקה כפולה | כל פעולת ניהול נבדקת **גם ב־Server Action** (`requireAdmin` / `requireProfessional`) **וגם ב־RLS**. הסתרת כפתור בצד הלקוח היא קוסמטיקה בלבד. |
| העלאות | `/api/upload` בודק **magic bytes** (ולא רק סיומת), גודל וסוג, מייצר שם קובץ אקראי, ומעלה עם `service_role` בשרת. מסמכי אימות נשמרים בדלי פרטי עם קישורים חתומים. |
| localStorage | משמש **רק** להעדפות ממשק (מצב תצוגה, לשונית אחרונה) ולטיוטות זמניות. שום נתון אמיתי אינו נשמר שם. |

### איך אימות בשם משתמש מתחבר ל־RLS

Supabase Auth דורש אימייל, והדרישה כאן היא **שם משתמש וסיסמה בלבד**. לכן האימות
נעשה אצלנו — **בתוך מסד הנתונים**:

1. הסיסמה נשלחת פעם אחת דרך TLS אל `auth_login()` — פונקציית `SECURITY DEFINER`.
2. הפונקציה מאמתת אותה מול **bcrypt** (`pgcrypto`), אוכפת הגבלת קצב ונעילה זמנית,
   ומחזירה **אסימון JWT חתום**.
3. **החתימה מתבצעת בתוך המסד** (`sign_jwt()`, HS256 מעל `hmac()`), עם מפתח שיושב
   בטבלה `app_secrets` שאין עליה שום הרשאה ל‑`anon` או ל‑`authenticated`.
4. `current_profile_id()` קוראת את `sub` מתוך ה־JWT, וכל מדיניות RLS נשענת עליה.

**למה זה חשוב:** זה מה שמאפשר ללקוח שרץ כולו בדפדפן (`index.html`) לעבוד בבטחה.
הדפדפן לעולם אינו מחזיק את מפתח החתימה, אינו גוזר סיסמאות ואינו רואה אף `hash` —
הוא מקבל רק אסימון חתום, ו־RLS ו‑Realtime אוכפים עליו הרשאות בדיוק כמו על השרת.

אפליקציית Next.js משתמשת באותן פונקציות (`hash_password` / `verify_password`),
ולכן לשני היישומים יש אותם משתמשים ואותן סיסמאות.

## הגדרת Supabase מאפס

1. **פרויקט חדש** ב־[supabase.com](https://supabase.com) (מומלץ אזור `eu-central-1`).
2. **Project Settings → API** — העתיקו:
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon public` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role` → `SUPABASE_SERVICE_ROLE_KEY`
   - **JWT Settings → JWT Secret** → `SUPABASE_JWT_SECRET`
3. **Project Settings → Database → Connection string (URI)** → `SUPABASE_DB_URL`
   (החליפו `[YOUR-PASSWORD]` בסיסמה האמיתית).
4. `npm run db:push` — יוצר את כל הטבלאות, הפונקציות, הטריגרים, מדיניות ה־RLS,
   דלי האחסון והפרסום ל־Realtime, וגם **מעביר את מפתח החתימה אל המסד**
   (נדרש כדי ש־`index.html` יוכל להתחבר). הסקריפט **אידמפוטנטי** — אפשר להריץ שוב.
5. `npm run db:seed` — נתוני הדגמה.

> אם אתם משתמשים רק ב‑`index.html` ואין לכם Node, אפשר להריץ את קובצי
> `supabase/migrations/*.sql` לפי הסדר ב‑SQL Editor של Supabase, ואז פעם אחת:
> ```sql
> select set_app_secret('jwt_secret', '<SUPABASE_JWT_SECRET שלכם>');
> ```
> בלי השורה הזו ההתחברות מהדפדפן תיכשל עם הודעה מפורשת.
6. ודאו ב־**Database → Replication** שהפרסום `supabase_realtime` כולל את
   `messages`, `conversations`, `notifications`, `bookings`, `booking_status_history`,
   `recurring_booking_series`, `post_likes`, `post_comments`, `professional_posts`,
   `follows`, `reviews` ועוד (מיגרציה `0013` עושה זאת אוטומטית).
7. ב־**Storage** ייווצרו הדליים: `avatars`, `covers`, `posts`, `messages`, `reviews` (ציבוריים)
   ו־`certificates` (פרטי — נגיש רק בקישורים חתומים).

## איך לבדוק שהכול עובד

### 1. הרשמה של משתמש רגיל
ההרשמה מבקשת **רק את ההכרחי**: שם, שם משתמש וסיסמה שהמשתמש ממציא.
העיר ושאר הפרטים מחכים בהגדרות ואינם עוצרים את הכניסה הראשונה.

1. `/register` → שם, שם משתמש (בדיקת זמינות חיה), סיסמה + אימות.
2. מד חוזק הסיסמה חייב להיות ירוק (8+ תווים, אות וספרה לפחות).
3. אחרי ההרשמה מוצג **קוד שחזור פעם אחת בלבד** — העתיקו אותו.
4. לחיצה על *המשך* מכניסה **ישר לפיד** — בלי שאלות ביניים.
5. `/settings` → מוצג באנר שמזמין להוסיף עיר, ולצידו הכפתור לפתיחת פרופיל עסקי.
6. בדיקה במסד: `select username, password_hash from profiles order by created_at desc limit 1;`
   — ה־Hash מתחיל ב־`$2` (bcrypt), והסיסמה לא מופיעה בשום מקום.
7. `/recover` → שם משתמש + הקוד שהעתקתם → סיסמה חדשה → התחברות מוצלחת.

### 2. הפיכה לבעל/ת עסק
1. `/settings` → **"אני בעל/ת עסק — פתיחת פרופיל עסקי"**. אפשר גם ישירות דרך `/pro/onboarding`.
2. עברו את 5 השלבים: פרטים → מיקום השירות → שירותים ומחירים → שעות → תיק עבודות.
3. שימו לב ל**מד ההשלמה** ולרשימת החוסרים — כפתור הפרסום נעול עד שכולם הושלמו.
4. בחרו **"מקצוע אחר"**, הקלידו שם חדש ושלחו. הפרופיל נשמר כטיוטה והבקשה נשלחת לניהול.
5. התחברו כ־`admin_yofi` → `/admin/professions` → אשרו את הבקשה.
   המקצוע נכנס לקטלוג ובעל המקצוע מופיע בקטגוריה החדשה **בלי שינוי קוד ובלי פריסה מחדש**.
6. חפשו את עצמכם ב־`/search` — הפרופיל החדש מופיע מיד.

### 3. הזמנה חד־פעמית
1. `/search` → "מניקור" → היכנסו לפרופיל → לשונית **שירותים** → **הזמנת תור**.
2. בחרו שירות, מיקום *"אצלי בבית"*, הוסיפו כתובת חדשה.
3. בבורר המועדים מוצגות **רק שעות פנויות** — הן מגיעות מ־`available_slots()` לפי שעות הפעילות,
   ההזמנות הקיימות, החסימות וזמן הנסיעה.
4. מסך הסיכום מציג מחיר כולל ומדיניות ביטול → **שליחת בקשה**.
5. התחברו כבעל המקצוע → `/dashboard/pro/bookings` → הבקשה שם, ו**הכתובת המלאה מוסתרת**.
6. לחצו **אישור** → הסטטוס הופך ל"אושר", **הכתובת נחשפת**, ללקוח נשלחת התראה,
   ובצ׳אט מופיעה הודעת מערכת.
7. נסו לקבוע הזמנה נוספת באותה שעה — המערכת חוסמת אותה (אילוץ במסד, לא רק בקוד).

### 4. מפגשים קבועים
1. בפרופיל בעל המקצוע → **קביעת מפגש קבוע** (`/book/recurring`).
2. בחרו תדירות (למשל *כל שבועיים*), יום, שעה ומספר מפגשים → מוצגת **תצוגה מקדימה של כל התאריכים**.
3. שלחו → הסדרה במצב *ממתין* עד שבעל המקצוע מאשר (**אישור דו־צדדי**).
4. `/dashboard/recurring/[id]` → **דלגו** על מפגש אחד, ו**הזיזו** מפגש אחר.
   סמנו *"לשנות גם את כל המפגשים העתידיים"* כדי לראות את ההבדל.
5. בעל המקצוע רואה את הסדרה ב־`/dashboard/pro/clients` יחד עם התדירות והערות פרטיות.

### 5. זמן אמת
1. פתחו שני דפדפנים (או חלון רגיל + פרטי) והתחברו כלקוח וכבעל מקצוע.
2. `/messages` בשני הצדדים → שלחו הודעה → היא מופיעה בצד השני **מיד, בלי רענון**.
3. אשרו הזמנה בצד אחד → בצד השני משתנה הסטטוס ומגיעה התראה בזמן אמת.
4. עשו לייק לפוסט בחלון אחד → מונה הלייקים בחלון השני מתעדכן.
5. כבו את החיבור לרגע — בחזרה למסך מתבצע רענון אוטומטי, כך שהמידע נכון גם בלי socket.

### 6. הרשאות
- התחברו כמשתמש רגיל ונסו לגשת ל־`/admin` → תופנו החוצה (גם ב־middleware, גם בשרת, גם ב־RLS).
- נסו לפתוח הזמנה של משתמש אחר לפי מזהה → נחסם.

## ביצועים

- **עימוד וגלילה אינסופית** בפיד, בחיפוש, בביקורות, בהודעות ובהתראות — אף מסך לא טוען הכול.
- **טעינה עצלה** לתמונות + `next/image` עם `sizes` מדויקים ו־`blur` placeholder.
- **דחיסת תמונות בדפדפן לפני ההעלאה** (`lib/upload-client.ts`) — חוסך רוחב פס ואחסון.
- **אינדקסים** על כל מפתח זר ועל כל עמודה שמסננים לפיה, כולל אינדקסי `GIN`/`pg_trgm` לחיפוש טקסט חופשי.

  ללא N+1.
- **`cache()` של React** על `getSession()` כך שאותו סשן נטען פעם אחת בכל בקשה.
- **`revalidatePath` ממוקד** אחרי כל פעולה — רק המסכים שהושפעו מתרעננים.

## החלטות תכנון

1. **אימות עצמאי במקום Supabase Auth** — הדרישה היא שם משתמש וסיסמה ללא אימייל.
   כדי לא לוותר על RLS, השרת חותם JWT תקף של הפרויקט, וכך כל שכבות ההגנה של Supabase נשארות פעילות.
2. **הלוגיקה הקריטית יושבת במסד** — מניעת חפיפה, תנאי פרסום, מעברי סטטוס וזכאות לביקורת
   נאכפים בטריגרים ובאילוצים. גם באג בקוד או קריאה ישירה ל־API לא יכולים לעקוף אותם.
3. **`blocked_until` כעמודה ולא כביטוי** — Postgres דורש `IMMUTABLE` באילוץ,
   ו־`timestamptz + interval` הוא `STABLE`. הטריגר מחשב את הערך מראש.
4. **טלפון וכתובת בטבלה נפרדת** — כך אי אפשר לחשוף אותם בטעות ב־`select *` על הפרופיל.
5. **הרשאות ברמת עמודה בנוסף ל־RLS** — הגנה שנייה שלא תלויה בכתיבת מדיניות נכונה.
6. **`datetime-local` תמיד נבנה ומומר דרך `lib/format.ts`** — ערבוב אזורי זמן בין חלקי המחרוזת
   יצר בעבר טווחים לא תקינים; שתי הפונקציות `toDateTimeLocalValue` / `fromDateTimeLocalValue` מונעות זאת.
7. **Realtime + רענון בחזרה למסך** — ה־socket הוא שיפור, לא תנאי לנכונות המידע.
8. **`index.html` כתוב ב‑CSS ידני ולא ב‑Tailwind CDN** — Play CDN מקמפל בדפדפן,
   מוסיף השהיית טעינה ואינו מיועד לייצור. ה‑CSS כאן משתמש **באותם משתני צבע** של
   אפליקציית Next.js, כך ששני היישומים נראים זהים ומצב כהה עובד בשניהם.
9. **הלקוח בדפדפן לא מנחש שגיאות** — `errorMessage()` מתרגם שגיאות Postgres מוכרות
   (חפיפת הזמנות, הפרת RLS, אסימון שפג) להודעות בעברית, במקום להציג טקסט טכני.

## הרחבות עתידיות

הקוד מחולק כך שאפשר להוסיף בלי לשבור:

- **תשלומים ומקדמות** — טבלת `payments` שמצביעה על `bookings`, ו־webhook שמעדכן סטטוס.
- **יומן חיצוני (Google / Apple)** — מנוי דו־כיווני מעל `professional_availability` ו־`unavailable_dates`.
- **מפה וחיפוש גיאוגרפי מתקדם** — `haversine_km()` כבר קיים; מעבר ל־PostGIS יאפשר חיפוש רדיוס מהיר יותר.
- **צ׳אט קבוצתי** — טבלאות ה־`conversations` / `conversation_members` כבר תומכות ביותר משני משתתפים.
- **וידאו וסטוריז** — `post_media` כולל `media_type`, כך שהוספת וידאו היא הרחבה ולא שינוי סכמה.
- **ריבוי שפות** — כל הטקסטים בממשק מרוכזים ברכיבים ובקבועים, מוכנים למעבר ל־i18n.
- **התראות Push מלאות** — הטבלה `push_subscriptions` וה־Service Worker כבר מוכנים; נדרש רק שירות שליחה.
- **אפליקציית מובייל** — כל הלוגיקה נמצאת ב־Server Actions וב־RPC, כך שלקוח נוסף יכול לצרוך אותה כמות שהיא.
